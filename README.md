Все этапы собраны в одном ноутбуке, чтобы решение было проще запускать и проверять. Зависимости указаны в requirements.txt.

### Какие данные и признаки использовала и почему
Для запроса использовала текст запроса `(search_query)`, категорию поиска `(search_category)`, локацию `(search_location_id)` и дополнительные параметры `(search_infm_params_text)`. 

Текст запроса описывает саму услугу, а остальные признаки позволяют заранее отсечь объявления по пользовательским фильтрам.

Для объявления использовала заголовок `(item_title_raw)`, параметры `(item_infm_params_text)`, описание `(item_description_raw)`, категорию `(item_category_id)`, микрокатегорию `(item_microcat_id)` и локацию `(item_location_id)`. 

Заголовок содержит самый короткий и точный смысл объявления, параметры — структурированную информацию, а описание помогает различать более похожие варианты.

### Какие модели и алгоритмы применила

Сначала по положительным взаимодействиям в тренировочной выборке для каждой категории поиска собрала множества категорий и микрокатегорий объявлений, которые реально выбирали пользователи с такой категорией запроса. 

Затем дополнительно фильтровала объявления по точной локации и параметрам запроса, поэтому вместо всего корпуса оставалось в среднем несколько тысяч кандидатов.

Оставшиеся объявления ранжировала с помощью BGE-M3. Выбрала её как готовую модель для семантического поиска, которая работает с русским текстом.

Запрос подавала в модель как текст запроса + дополнительные параметры, чтобы эмбеддинг учитывал и основную формулировку, и выбранные пользователем фильтры. 

Объявление подавала как заголовок + параметры + описание, чтобы собрать всю доступную текстовую информацию в одном представлении.

BGE-M3 отдельно строит эмбеддинг для каждого запроса и объявления. После L2-нормализации считала cosine similarity между эмбеддингом запроса и каждым оставшимся кандидатом: чем выше значение, тем ближе тексты по смыслу. Для каждого запроса сортировала кандидатов по этой близости и брала первые 50.

### Как проверяла качество

Локально разделила тренировочную выборку на тренировочную и тестовую по тексту поискового запроса, чтобы одинаковые запросы не попадали одновременно в обе части. В финальном решении это разделение удалено, и вся тренировочная выборка используется для построения фильтров.

### Какие ошибки нашла и что изменила

Долго не могла понять, что сначала надо сужать поле поиска фильтрами. Пробовала BM25, Tantivy, BGE, reranker, ColBERT и CatBoost, но Recall@50 не получалось поднять выше 0.2. Главная ошибка была в том, что я сразу искала среди всех объявлений, хотя большую часть можно заранее отсечь. После этого вынесла категорию, микрокатегорию, локацию и параметры в жёсткие фильтры, а BGE оставила только для ранжирования оставшихся кандидатов. Это и дало основной прирост до 0.65 Recall@50.

### Точки роста

Это мой первый опыт с поисковой системой, не все идеи успела реализовать. Идею с жёсткими фильтрами я взяла из описания архитектуры поиска Авито (https://vc.ru/id3843321/1657073-kak-ustroena-poiskovaya-vydacha-na-avito-podrobnyi-razbor). 

Дальше я бы добавила запасной сценарий для слишком узких или пустых выдач (ослабление фильтров, поиск по векторам https://avito.tech/content/je6de84u31-kak-rabotaet-poiskovoe-ranzhirovanie-dly, объявления из других городов с доставкой). Ещё можно сделать многоступенчатое ранжирование и учитывать не только текстовую релевантность, но и рейтинг, количество отзывов, цену и другие доступные признаки объявления.
